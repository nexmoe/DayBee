# 子系统参考

这里的页面描述**当前已实现**的职责、运行路径、状态和契约。改一个有文档的子系统之前，先读对应页，再沿页里的源码链接核对你要改的实现。

一个子系统按功能切，不按目录切，可以横跨 Go 后端、渲染进程和共享 package。页面写这些部分合在一起提供的行为，不用列出每个函数。

## 维护一页

契约变了，同一个 PR 改对应页。契约指职责、接口、状态转换、运行路径、兼容规则或失败行为。保持这些不变的内部重构不用改文档。

一个事实只写一处，别处链过来。写到源码时写文件和符号，不要抄会频繁变动的实现细节；签名本身看不出的字段含义和约束才写下来。常量写成"名（值）"。

每页写这几节，没有就补：

- 职责与边界：管什么，不管什么，每一行对到源码。
- 权威来源：哪个文件或状态是唯一事实。
- 运行路径：一次请求、事件或状态变化实际走过哪些步。
- 约束与失败行为：限时、阈值、出错谁兜底、兼容怎么处理。
- 验证：能直接跑的测试或检查命令。

只写已实现的状态。方案、重构设计和一次性计划放 issue、PR 或 `docs/superpowers/`，落地后再把长期事实写回这里。文档里点名的安全缺口是一个没关闭的 bug，写下这种句子时在同一个提交里开 issue。

## PR 怎么写

每个受影响的子系统写清：什么条件触发，改前怎么行为，改后怎么行为。接口、状态、兼容或失败行为有变化时一并写上。链到受影响的页面、实现和验证证据。重构保持文档描述的行为不变时，直接说明。

例如，改录音恢复的 PR 要说明：哪种中断会触发恢复，恢复前未完成的分段落到哪、之后落到哪，哪个测试覆盖这次切换。

这是作者给的说明，评审对着 diff 和周围代码核实。它不是自动得出的兼容性结论。

## 评审一个改动

1. 找出受影响的子系统和真实运行路径，包括走 Go 后端、渲染进程还是 Web，走哪个平台。
2. 对照代码，核对 PR 说的改前改后行为。追到改动行之外的调用方和状态转换。
3. 查文档是否更新，源码链接是否还能打开。`bun run check:docs` 必须零错误。
4. 查引用的测试或运行证据是否覆盖声称的行为。没跑的检查如实写明。

只改文档证明不了实现。行为变了，仍然要有测试或运行证据。

## 谁来守

`bun run check:docs` 对 `docs/subsystem/` 强制检查：相对链接的目标文件存在，反引号里以 `apps/`、`packages/`、`scripts/`、`docs/`、`.agents/`、`.github/` 开头的路径存在。写着删除、移除的行不查。它不查锚点，不查语义，也发现不了没写进文档的契约。语义靠评审。

同一个命令会顺带报告 `docs/` 其他目录的失效引用，但那些不导致失败。

CI 里 `.github/workflows/desktop-release.yml` 的 `native` 任务在装完依赖后就跑它，每个 PR 都会触发。它不依赖构建产物，几秒跑完。
